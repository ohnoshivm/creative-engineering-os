## Use during a project

1. Choose two or three references that address a named problem. Record the project goal, source URL and access date.
2. Inspect the actual experience before asserting anything about its visuals, timing, performance or accessibility. Capture desktop and mobile evidence for a visual study.
3. Extract principles: hierarchy, scale, rhythm, contrast, feedback, camera intent, rendering strategy. Write what each principle accomplishes for the user.
4. Close the source and sketch an original composition using the project's own content, identity and constraints.
5. Build the smallest useful exercise; measure it on the target devices. Keep the source, hypothesis, screenshot/trace and conclusion together in the project's evidence folder.

Never reuse reference copy, logos, imagery, code or distinctive compositions without the applicable rights. Public access does not grant reuse rights. Free-to-read, open source, and commercially licensed are different categories. Pricing, license terms and browser support must be rechecked before procurement or adoption.

## Difficulty and evidence

Beginner assumes basic HTML/CSS/JavaScript; intermediate assumes a working app and debugging skills; advanced assumes graphics or animation fundamentals. Difficulty, strengths, limitations and exercises are editorial judgments, not claims made by the source authors.

“Verified” below means a live first-party page/repository was retrieved on the stated date; it is not a completed course, runtime test, license audit or visual review. Shell-only and blocked checks remain marked. All exercises are proposed work, not completed evidence.

## Maintain

Before using a resource, recheck its canonical link and relevant package/release documentation. Review this index quarterly; mark redirects, access restrictions and retired resources instead of silently treating them as healthy. Keep summaries short and original. Record actual verification dates only after a live check.
